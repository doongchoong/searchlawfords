# 법규 검색

증권사 현업이 모든 증권사 공통 준수사항의 근거 조문을 빨리 찾도록 돕는다. 사람이 확정한 과거 조회 경로(사례)를
먼저 보여 주되, 답변에 쓰는 본문과 개정일은 매번 사이트에서 다시 확인한다.

- **하는 일**: 근거 규정·조문 찾기, 조문 발췌, 사이트상 개정일·본문 수집일·원문 링크 제시, 최근 제·개정과 개정예고 안내, 확정한 경로를 사례로 쌓기.
- **하지 않는 일**: 적법·위법 결론 단정, 회사 고유 상품·내부 문서, 캡차·봇 차단 우회, 규정 원문 통째 반출.

## 준비

- **스킬 폴더**는 이 `SKILL.md`가 있는 폴더다. 아래 명령의 `<스킬>`을 그 절대 경로로 바꿔 실행한다. 예: `<PY> "<스킬>/scripts/match.py" "질문"`.
- **Python 고르기** — 아래 명령의 `<PY>`는 다음 순서로 정한 Python이다. 대화에서 한 번 정하면 계속 쓴다.
  1. `<스킬>/runtime/python/python.exe`가 있으면 그것(스킬에 동봉된 Python, 설치 불필요). 경로는 따옴표로 감싼다.
  2. 그게 없거나 실행이 막히면(“액세스가 거부되었습니다”, “응용 프로그램 제어 정책” 등 보안 프로그램 차단) `py -3 --version`, `python --version`을 차례로 확인해 3.10 이상이 나오는 명령. 아무것도 안 나오거나 Microsoft Store가 열리면(경로에 `WindowsApps`) 설치된 Python이 없는 것이다.
  3. 둘 다 안 되면 조회하지 말고 `<스킬>/references/python-install.md`를 읽어 그 안내를 사용자에게 보여 준다. 동봉 Python이 막혀서 이 단계에 온 거라면 그 사실도 함께 알린다.
- 결과는 모두 JSON(UTF-8)으로 나온다. 사용자 데이터(카탈로그·캐시·사례집·스크린샷)는 `%LOCALAPPDATA%\regulation-search\`에 있다.
- 이 PC에서 처음 쓰는 것 같거나 Chrome·Python 오류가 나면 먼저 `<PY> "<스킬>/scripts/check_env.py"`를 돌린다. 실패 항목이 있으면 조회하지 말고 그 결과를 사용자에게 알린다.
- 명령마다 헤드리스 Chrome을 새로 띄우고 요청 사이에 2초씩 쉰다. 온라인 매칭은 수십 초 걸리니 사용자에게 "사이트를 확인하는 중"이라고 한 줄 알린다.

## 질문 유형 고르기

| 유형 | 예 | 하는 일 |
| --- | --- | --- |
| 직접 지정 | "자본시장법 제9조", "매매거래계좌설정약관 6조", "시장감시규정 회원의 금지행위" | 바로 `lookup.py article` |
| 근거 탐색 | "고객 주문 없이 매매하면 안 되는 근거는?" | 아래 "근거 탐색 절차" |
| 변경 확인 | "최근 한 달 바뀐 KRX 규정", "개정 예고 중인 거 있어?" | `lookup.py recent`만. 본문은 가져오지 않는다 |

사이트 고르기: 협회 규정·모범규준·표준약관·표준내부통제기준 → KOFIA. 거래소 업무·상장·공시·시장감시·회원·청산결제 규정 → KRX. 법률·시행령·시행규칙과 금융위 고시(금융투자업규정, 금소법 감독규정) → 법제처. 모르면 매칭에 맡긴다.

## 근거 탐색 절차

질문을 이해하는 건 Claude가, 찾고 확인하는 건 스크립트가 한다. 스크립트의 자동 키워드 추출은 조사·어미를 떼는 규칙 수준이라
("만료되는", "관리종목인" 같은 말에 약하다), 반드시 0단계의 해석을 먼저 하고 그 결과를 넘긴다.

0. **질문 해석(Claude)**: 질문을 읽고 아래 네 가지를 정한다. 사용자에게 따로 보여 줄 필요는 없다.
   - **핵심어**(`--terms`): 질문의 생활어를 규정 본문에 실제로 쓰이는 용어로 바꾼 2~6개. 예: "투자자정보 만료" → `투자자정보, 유효기간` / "고객 몰래 매매" → `임의매매, 주문을 받지 아니하고` / "투자성향 확인" → `투자자정보, 적합성원칙`. "신경써야", "정리" 같은 말이나 너무 흔한 말("고객", "증권")은 넣지 않는다.
   - **짚이는 규정**(`--regs`, 있을 때만): 질문에 나오거나 분명히 떠오르는 규정의 정식명·약칭. "사이트:이름"도 된다(예: `KOFIA:표준투자권유준칙`, `금융투자업규정`). 확신이 없으면 비운다. 매칭이 나머지를 찾는다.
   - **사이트 검색어**(`--search`, 1~2개): 사이트 통합검색에 넣을 가장 구체적인 말. 공백이 있으면 `--search "투자자정보 유효기간"`처럼 따옴표로 묶고 여러 번 준다. "만료", "유효기간"처럼 다른 맥락에서도 흔한 말을 혼자 넣지 말고 대상과 묶는다.
   - **업무영역**(`--areas`, 있을 때만): `references/scope.json`의 영역 이름(자본시장 일반, 금융소비자보호, 실명거래·자금세탁방지, 신용정보·전자금융, 세제).
   - **주의**: 해석은 "어디를 찾을지"까지만이다. 기억하고 있는 조문 번호·내용을 답에 쓰지 않는다. 답의 근거는 2단계에서 라이브로 확인한 본문뿐이다.
1. **후보 찾기**: `<PY> "<스킬>/scripts/match.py" "<질문 그대로>" --terms "<핵심어,…>" [--regs "<규정,…>"] --search "<검색어>" [--search "<검색어2>"] [--areas "<영역>"] --online --json`
   - 결과의 `candidates` 순서가 "처음 후보"다. 확정 초안에 그대로 넣으므로 이름 목록을 기억해 둔다(`사이트:규정명`).
   - 후보마다 `reasons`(왜 후보인지)가 있다. 사용자에게 보여 줄 때 이유를 한 줄씩 붙인다.
   - **후보를 그대로 믿지 말고 읽고 거른다.** 이름이나 검색어만 우연히 겹친 후보(예: 질문은 투자자정보인데 "추천의 유효기간"이 걸린 규정)는 답변 근거에서 뺀다.
   - **사례는 Claude가 판단한다.** `cases`(점수가 넉넉한 것)와 `cases_considered`(문턱 아래까지 넓게)의 `주제`·`서술`을 읽고 정말 같은 주제인 사례만 출발점으로 쓴다. 쓴 사례는 경로를 먼저 보여 주되, 사례와 무관한 후보(`sources`에 case가 없는 것)도 반드시 함께 본다.
   - 사례에 `개정이후미확인`이 있으면 `<PY> "<스킬>/scripts/cases.py" relocate <사례id>`로 조문 제목 기준 현재 위치를 다시 찾는다.
   - 후보가 엉뚱하면 해석을 고쳐 한 번 더 돌린다(핵심어·검색어를 바꾸거나, 찾은 조문이 인용하는 상위 규정을 `--regs`에 넣는다).
   - 빨리 훑어만 볼 때는 `--online` 없이 돌려도 되지만(카탈로그와 캐시만 사용), 답변 근거는 반드시 다음 단계의 라이브 확인을 거친다.
2. **본문 확인(라이브)**: 상위 후보 2~3개에 대해
   - 규정 안에서 맞는 조문 찾기: `<PY> "<스킬>/scripts/lookup.py" find --site <KOFIA|KRX|법제처> --reg "<규정명·약칭·ID>" --query "<핵심어를 띄어 쓴 것>"` (질문 원문보다 0단계 핵심어가 정확하다)
   - 찾은 조문이 다른 조문을 근거로 적고 있으면(예: "☞ 금융투자업규정 제4-73조") 그 조문도 `article`로 열어 확인한다.
   - 조문 하나 보기: `<PY> "<스킬>/scripts/lookup.py" article --site <사이트> --reg "<규정>" --number <조번호> [--title "<조문 제목>"]`
   - 본 규정과 시행세칙을 함께 본다(KOFIA·KRX는 "○○규정 시행세칙", 법제처는 법·시행령·시행규칙). 짝은 매칭 결과에 `pair`로도 나온다.
   - 결과의 `시점`을 답변에 그대로 옮긴다. `--no-verify`로 얻은 결과는 답변 근거로 쓰지 않는다.
3. **교차 확인(필요할 때)**: `<PY> "<스킬>/scripts/lookup.py" search "<핵심어>" [--site 법제처]`. 법제처 결과의 `extra.in_scope`가 false면 화이트리스트 밖 법령이라 "범위 밖"으로 표시하고, `extra.status`가 시행예정이면 "시행예정 개정판 있음(본문 미확인)"으로 적는다.
4. **답변**: 아래 출력 형식으로 쓴다.
5. **확정 초안 만들기(필수)**: 답변을 쓰기 전에 **반드시** 초안 명령을 실행한다. 경로를 말로만 나열하지 않는다.
   - `<PY> "<스킬>/scripts/cases.py" draft "<주제>" --path "<사이트>|<규정>|<조번호>" [--path …] --first "<처음 후보1>" --first "<처음 후보2>" … [--law-query "<법제처에서 쓴 검색어>"] --terms "…" [--regs "…"] --search "…" [--areas "…"]`
     - 1단계에 넘긴 해석(`--terms/--regs/--search/--areas`)을 **그대로** 함께 넘긴다. 사례의 `해석`으로 저장되어 다음 비슷한 질문의 사례 찾기와 매칭 평가에 쓰인다.
     - `주제`는 질문을 한 줄로 다듬은 문장(예: "위탁매매 업무에서 고객 주문 없이 매매하지 않을 준칙").
     - 근거로 쓴 조문만 `--path`로 넣는다. 조번호는 `17`, `4-20`, `56의4`, `8`(모범규준식 "8.")처럼 쓴다. "제N조의M"은 `56의4`로 쓰는 게 정확하다(`56-4`도 "제56-4조"가 없으면 "제56조의4"로 찾는다).
     - `--first`에는 1단계 매칭 결과의 `candidates` 순서 그대로 `사이트:규정명`을 넣는다.
   - 출력은 `{"file": 초안 파일 경로, "draft": {…}}`이다. 초안은 파일로만 남고 사례집에는 아직 아무것도 쓰지 않는다.
   - `draft.경로`에 `확인필요`가 붙은 칸은 조문 제목을 못 채운 것이다. 2단계에서 확인한 조문 제목을 초안 파일에 직접 채운다.
6. **확정 질문(한 번만)**: 답변 맨 끝(출력 형식의 "확정 초안")에 초안의 `서술`과 경로를 그대로 보여 주고 **"이 경로를 이력으로 확정할까요?"**라고 한 번만 묻는다.
   - 그대로 승인 → `<PY> "<스킬>/scripts/cases.py" confirm --latest`(또는 `--file <초안 파일>`).
   - 고쳐서 승인 → 초안 파일을 고친 뒤 `confirm --file <초안 파일>`.
   - 결과의 `action`(추가/재확정)과 `id`를 한 줄로 알린다.
   - 거절하거나 답이 없으면 → 아무것도 하지 않는다(초안 파일은 그대로 두어도 된다).
   - "해당없음"(근거 규정이 없다는 확정)은 사용자가 명시적으로 그렇게 확정할 때만 `--none`으로 만든다.

## 직접 지정·변경 확인

- 직접 지정: `lookup.py article`로 조문을 가져와 출력 형식대로 답한다. 번호가 개정으로 밀렸을 수 있으니 사용자가 제목을 말했으면 `--title`도 준다. 확정 질문은 근거 탐색과 같다.
- 변경 확인: `<PY> "<스킬>/scripts/lookup.py" recent --days <일수> [--site …]`. 제·개정(`kind: 제개정`)과 예고(`kind: 예고`)를 나눠 보여 준다. KRX 예고는 종료일이 사이트에 없다. 법제처는 화이트리스트 법령의 현행 시행일만 본다. 사례 확정은 묻지 않는다.

## 출력 형식

```markdown
**결론**: (한 줄. 근거 규정 요약이며 적법성 단정이 아님)

**근거 조문**
- 규정명 제N조(조문 제목) 제M항 — 구분: 현행 | 시행예정 | 개정예고
  > 필요한 문장만 발췌
- 본 규정과 시행세칙을 함께 본 경우 둘 다 표기

**시점**: 사이트상 개정일 YYYY-MM-DD / 본문 수집일 YYYY-MM-DD
**원문 링크**: (조문 링크. KRX는 첫 화면 URL + 찾아가는 경로)
**참고한 확정 사례**: c-202610-001 (있을 때만)
**확인하지 못한 부분**: (미확인·접근 실패·범위 밖)

※ 법률 자문이 아니라 근거 자료 제시입니다.

**확정 초안** (cases.py draft 결과 그대로)
- 서술: (draft.서술)
- 경로: (draft.경로를 한 줄씩: 사이트 / 규정 / 조문(제목) / 개정일)

이 경로를 이력으로 확정할까요?
```

## 규칙

- 근거 자료 제시임을 밝히고 적법·위법 결론을 단정하지 않는다.
- 검색 결과가 0건이어도 "관련 규정 없음"으로 단정하지 않는다. 검색한 범위(KOFIA·KRX 현행 규정 전체, 법제처는 화이트리스트와 조문내용 검색)와 못 본 범위를 밝힌다.
- 현행·시행예정·개정예고를 항상 구분한다. 법제처 시행예정 개정판 본문은 아직 열지 못하므로 존재만 알린다.
- 시점은 사이트상 개정일과 본문 수집일을 함께 적는다. `lookup.py`가 현재 개정판을 확인하고 바뀌었으면 다시 받으므로, 그 결과의 값을 쓴다.
- 확정 사례는 출발점으로만 쓴다. 사례에 적힌 내용이 아니라 매번 라이브로 확인한 본문으로 답한다.
- 규정 본문은 필요한 조문 범위만 발췌하고 원문 링크를 붙인다.
- 조회 결과의 조문에 `분할`(또는 매칭 결과에 `parse`: rough/block)이 있으면 사이트 구조가 아니라 본문 글자 모양으로 나눈 것이다. 근거 조문 줄에 "(자동 분할)"을 붙이고, `블록N`은 정식 조문 번호가 아니므로 번호 대신 "규정명 중 '첫 문장…' 부분"처럼 쓰며 원문 링크로 확인하라고 적는다.
- 명령 결과에 "차단·캡차 화면으로 보여 중단합니다"(BlockedError)가 나오면 즉시 멈추고 스크린샷 경로와 함께 사용자에게 알린다. 다시 시도하거나 우회하지 않는다.
- 확정 질문은 답변 끝에 한 번만 한다. 그 전에 반드시 `cases.py draft`로 초안을 만들어 보여 준다. 사용자가 승인·수정하지 않은 경로는 저장하지 않는다.

## 명령 요약

| 명령 | 용도 |
| --- | --- |
| `scripts/check_env.py` | 환경 점검(처음 한 번) |
| `scripts/match.py "<질문>" --terms … --search … [--regs …] [--areas …] [--online] [--json]` | 질문 해석을 받아 후보 규정·조문과 이유, 유사 사례 |
| `scripts/lookup.py article|find|recent|search …` | 라이브 본문·조문, 최근 변경, 사이트 검색 |
| `scripts/cases.py draft|confirm [--latest]|list [--stale]|relocate <id>` | 확정 초안(파일로 저장)·확정·목록·개정 후 위치 재확인 |
| `scripts/catalog.py stats|refresh [--site …]` | 통합 카탈로그 확인·갱신(새 규정이 안 잡힐 때) |
| `scripts/eval.py [--online|--cases]` | 매칭 회귀 평가(개발용) |

## 문제가 생기면

- 조회가 깨지면 사이트 화면이 바뀐 것일 수 있다. 오류 메시지의 스크린샷 경로를 알리고, 개발자에게 `references/selectors.<사이트>.json` 확인을 요청하도록 안내한다.
- 새로 생긴 규정이 후보에 안 나오면 `catalog.py refresh`로 카탈로그를 갱신한다(1~2분).
- 약칭이 안 통하면 `references/aliases.json`에, 법제처 법령이 범위 밖으로 나오면 `references/scope.json`에 추가하자고 사용자에게 제안한다(직접 고치지 않는다).
